# usage-sentinel：假設驗證與需求衝突

> 對應《usage-sentinel-需求書.md》。環境：Windows 11、VS Code 擴充套件（內建 Claude Code 2.1.296）、CLI 2.1.293、Pro 方案、Node 22。
> 主要情境：**有明確 plan 文件的長任務**（一個 prompt 跑很久，中間少有人互動）。
> 狀態：✅ 成立 ❌ 不成立 ⚠️ 部分成立 🧪 待實測 📄 依官方文件

## 2. 實驗紀錄

實驗目錄：`scratchpad/exp`（專案層級 `.claude/settings.json`，不動全域設定）。`log.mjs` 記錄每次 hook/statusLine 的輸入與環境，並依 `resp/<tag>.json` 規則回應。

| 代號 | 方式 | 耗時 |

| E3 | 同一指令分別回 silent / allow / ask / deny（含一個需核准的寫檔指令） | 3 分 |
| E4 | hook 逾時、exit 1、`continue:false`（主 agent／只對 subagent） | 3 分 |
| E5 | Node → PowerShell WinForms 三按鈕對話框，20 秒逾時 | 1 分 |
| E6 | 2 寫 3 讀壓測 rename 5 秒；12 程序搶 mkdir 鎖 × 5 | 1 分 |
| U1–U3 | VS Code 互動 session（auto 模式）跑 5 步，見第 5 節；紀錄存於 `log-interactive-U1.jsonl` | 5 分 |

## 3. 需求書內部衝突

| # | 衝突的條目 | 衝突內容 | 建議解法 |
|---|---|---|---|
| C1 | FR-7「安裝腳本註冊 hooks 到 settings.json」 vs §8 交付物 `hooks/hooks.json` | 兩邊都註冊會各跑一次 → 兩個對話框（A19） | 用 plugin 的 hooks.json；FR-7 只負責 statusLine |
| C2 | FR-4.6「繼續 → 輸出 `allow`」 vs 非目標「不修改權限模式」 | `allow` 會跳過原本的權限確認（A8） | 繼續 → 不輸出決策 |
| C3 | FR-4.4「逾時視為停止」 vs §6「hook 出錯一律放行」 vs 平台行為「hook 逾時 → 放行」 | 若對話框卡住超過 hook timeout，結果變成放行，與「停止」相反（A12） | 對話框逾時由 hook 內計時器處理；鎖的等待者也要有上限；明訂 fail-open/closed 原則 |
| C4 | FR-4.2「用量再上升 4% 才再問」 vs §6「到 stop + snooze_step 再問」 vs 驗收 2「升到 97% 前不再詢問」 | 93% 按繼續：前者 = 97%，後者 = 96% | 擇一；建議以「按下時的百分比 + step」為準 |
| C5 | FR-4.2「繼續到重置前都不要再問」 vs §6「99% 不論 snooze 都再問」 | 優先順序未定 | 明訂 99% 優先 |
| C6 | FR-4.2「7 天視窗需二次確認」 vs FR-7「hook timeout = prompt_timeout + 30」 | 兩個對話框最多 90 + 90 秒 > 120 秒 → hook 逾時 → 放行 | 二次確認共用同一個逾時預算，或 timeout 改為 2×prompt + 30 |
| C7 | FR-4.5「`-p` 模式直接視為停止」 vs FR-3「沒資料就不阻擋」 | `-p` 沒有 statusLine（A1），通常沒新鮮資料 → 永遠走「不阻擋」，`-p` 規則幾乎不會觸發 | 決定 `-p` 是否支援；支援就需要別的資料來源 |
| C8 | FR-2「warn／wind-down 由 UserPromptSubmit 注入」 vs §1 目標 2「接近上限時先收尾」 | 長任務期間 UserPromptSubmit 不觸發（A5） | 改由 PreToolUse 注入（A5'） |
| C9 | 驗收 7「settings.json 恢復成安裝前內容」 vs FR-7「移除 hooks、還原 statusLine」 | 整份還原會吃掉安裝後使用者自己的修改 | 只移除／還原本工具改過的欄位 |
| C10 | 設定鍵 `wind_down_allowed_tools` vs FR-4.6 在 **stop** 階段使用 | 名稱與用途不符；wind-down 階段到底有沒有強制限制不清楚 | 改名 `stop_allowed_actions`，並寫明 wind-down 只建議不強制 |
| C11 | FR-1「沒有 `rate_limits` 不覆寫舊資料」 vs 📄 平台「`resets_at` 一過就移除該視窗」 | 重置後仍沿用舊的 95%，最多誤擋 `stale_after_seconds`（10 分鐘） | 判斷時 `resets_at < now` 的視窗視為 0% |

| C12 | FR-4.6「收尾後輸出 `{"continue": false}`」 vs 驗收 3「Claude 只做 commit 與 RESUME.md 然後結束」 | 單獨的 `continue:false` 不擋當次工具；遇到被權限流程拒絕的呼叫時甚至不會停（A11'） | 停止輸出改為 `deny` + `continue:false` |

## 5. 互動實驗步驟（U1–U3，已執行）

1. 在 VS Code 用「開啟資料夾」打開 `scratchpad\exp`（完整路徑見對話），開一個**新的** Claude Code 對話（保持你平常的權限模式）。
2. 貼上這段 prompt：
   ```
   依序執行，每一步一個 Bash 呼叫，不要平行、不要合併：
   1. sleep 20; echo step1
   2. sleep 20; echo step2
   3. echo ASK_TEST
   4. echo BLOCK90
   5. echo STOP_TEST
   ```
3. 觀察並記下：
   - 底部是否出現 `EXP-SL` 狀態列文字（U1）
   - 第 3 步是否跳出確認提示、提示文字是什麼（U2 / A9'）
   - 第 4 步 hook 會卡 90 秒：畫面是否出現「無回應」之類的警告（U3）
   - 第 5 步是否看到「usage-sentinel 測試：已達 92%…」的停止原因（A20）
4. 回來告訴我觀察結果，我會讀 `log.jsonl` 補齊 A2、A3、A17。

## 7. B 方法實驗結果（E8，2026-10-12，Windows + Pro）

憑證：`~/.claude/.credentials.json` → `claudeAiOauth.accessToken`（含 `user:profile` scope；token 數小時到期，由 Claude Code 自行刷新，**守衛只能每次重讀檔案，絕不可自己刷新**，否則 token 輪替可能讓 Claude Code 被登出）。

| | ① usage 端點 | ② probe header |
|---|---|---|
| 請求 | `GET https://api.anthropic.com/api/oauth/usage`，header `Authorization: Bearer`、`anthropic-beta: oauth-2025-04-20` | `POST /v1/messages`，`max_tokens: 0`，同樣 OAuth header |
| 結果 | ✅ HTTP 200，300–500ms | ✅ HTTP 200，約 700ms；`max_tokens: 0` 被接受 |
| 數值 | `five_hour.utilization: 38.0`、`seven_day.utilization: 31.0`（0–100） | `anthropic-ratelimit-unified-5h-utilization: 0.37`、`7d-utilization: 0.31`（**0–1**） |
| 重置時間 | ISO 字串（含微秒），如 `2026-10-12T06:40:00.833252+00:00` | epoch 秒，如 `1791787200` |
| 額外資訊 | `limits[]` 有 `severity`、`is_active`；還有 Opus/Sonnet 分項等欄位（Pro 目前為 null） | `5h-status`／`7d-status`（`allowed` 等）、`representative-claim`（目前由哪個視窗主導） |
| 頻率限制 | ❌ **約 1 分鐘內第 5 次起 429，`retry-after: 300`（鎖 5 分鐘）** | 未觸發；但每次都是一次推論請求，會耗一點額度（34 input tokens） |
| 風險 | 未公開、欄位命名大量內部代號，隨時可能改；被鎖時可能連帶影響 Claude Code 自己的 `/usage` 面板（同一個 token，未驗證） | 未公開；需要冒用 Claude Code 的 system prompt 才能用訂閱 token 推論，**可能違反訂閱條款**，不建議 |

發現：
- 需求書 §2 寫「`resets_at` 曾見過 epoch 與 ISO 兩種格式」，原因找到了：statusLine／header 用 epoch，usage 端點用 ISO。
- 百分比的單位也不一樣（0–100 與 0–1），解析時要正規化。
- 兩個來源同一時間差 1%（38 vs 37），可能是四捨五入或取樣時間差。

設計含意（若採 B 方法 ①）：
- 全機只能有**一個**輪詢者：用鎖 + 共用快取檔，所有 hook 只讀快取。
- 輪詢間隔建議 ≥ 120 秒；收到 429 必須遵守 `retry-after`，期間沿用快取並標示資料年齡。
- 長任務期間用量上升速度有限，2 分鐘一次的解析度對 75／85／92 三段門檻已足夠；但 92% 附近一回合就可能跳過幾個百分點（見盲點 12）。

## 8. `claude plugin uninstall` 研究（E9，2026-10-12）

### 8.1 官方文件與本機 `--help`（CLI 2.1.293）

- 語法：`claude plugin uninstall|remove <plugin> [--scope user|project|local] [--keep-data] [--prune] [-y] [--json]`，`--scope` 預設 `user`。
- 從**最後一個**安裝範圍移除時，會刪除 plugin 的 options／secrets 與資料夾 `~/.claude/plugins/data/<id>/`（`--keep-data` 例外）。
- 失敗時 exit 1；`--json` 有 `failureCode`（例如 `settings_still_on`）、`keptData`。
- 執行中的 session 要 `/reload-plugins` 或重開才會套用變更。
- plugin **沒有**安裝／移除生命週期 hook：#9394、#13704 都是功能請求，已被自動關閉。也就是說，plugin 被移除時，沒有機會執行自己的清理程式。

### 8.3 參考專案的移除做法

| 專案 | 移除方式 | 留下的東西 |
|---|---|---|
| heavyc-dev/heavy-usage | 沒有移除指令；README 請使用者手動還原備份、刪資料夾、再執行 `claude plugin uninstall` | 安裝時把**絕對路徑**寫進 statusLine，plugin 更新後就會失效；另外會修改全域 `CLAUDE.md` |
| denverbaumgartner/usage-guard | 沒有；statusLine 由使用者自己手動貼上 | 全部要手動清 |
| ManvikPasula/usage-guard | `/usage-guard uninstall`：statusLine 指向自己時才還原成原本的指令（或刪除），並先備份 | 狀態資料夾、備份檔、plugin 本體都還在。值得借鏡的兩點：① statusLine 指向狀態資料夾裡的 **shim**，由 SessionStart 在 plugin 路徑變動時更新；② 用隔離的 `CLAUDE_CONFIG_DIR` 做完整的安裝→移除往返測試 |

### 8.4 本機實驗：隔離的 `CLAUDE_CONFIG_DIR`，搭配你 settings.json 的副本

| 步驟 | 觀察 |
|---|---|
| install | 新增：`plugins/cache/<市集>/<plugin>/<版本>/`、`plugins/installed_plugins.json`、`plugins/known_marketplaces.json`、settings.json 的 `enabledPlugins` 與 `extraKnownMarketplaces` |
| uninstall | ✅ `enabledPlugins` 項目移除；✅ `plugins/data/<id>/` 刪除。❌ **cache 資料夾留著**，只多了一個 `.orphaned_at` 標記（由 Claude Code 之後自行回收）。❌ 市集宣告（`extraKnownMarketplaces`）仍在 |
| marketplace remove | 市集宣告移除；cache 仍帶著 `.orphaned_at` |
| 副作用 | ⚠️ 第一個會寫入設定的 plugin 指令（`marketplace add`）就把你的 `"model": "opus"` 改寫成 `"opus[1m]"`。這是 Claude Code 寫入設定時的正規化，跟 #84867 屬於同一類問題（重寫時會改動無關的鍵）。其他鍵沒有變動 |

結論：
1. 只靠 `claude plugin uninstall` **一定會有殘留**：cache 資料夾、市集宣告、我們自己的狀態資料夾與 statusLine 設定。
2. **舊 session 的 hooks 會繼續從殘留的 cache 路徑執行**，直到重開或 `/reload-plugins`。所以守衛必須在「狀態資料夾不存在」時什麼都不做，而且**絕不能自己重建狀態資料夾**，否則一移除完就會被舊 session 長回來。
3. 任何會寫 settings.json 的操作都要先備份、事後比對差異。
